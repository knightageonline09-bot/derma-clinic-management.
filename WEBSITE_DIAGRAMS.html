Derma Clinic Management System

Website structure, role access, and system architecture

Companion diagrams for the thesis document. Every label, panel and permission shown here is taken from the running system.

Figure 1 — Website navigation map

The login screen is the only entry point. A successful sign-in returns a JSON Web Token carrying the user's role, and that role determines which of the twelve sidebar entries the shell renders.

Figure 2 — Role access map

Four system roles are defined. Each role receives only the sidebar entries listed for it; every other workspace is hidden, and the corresponding interface elements are not rendered. Therapists are personnel records, not roles, and never sign in.

Point to raise if asked. A role can be permitted to read a dataset without having a workspace for it. Receptionist may read the inventory endpoint, because the treatment docket form shows a live stock check, even though neither role has an Inventory workspace. Interface visibility and endpoint authorization are therefore two separate layers, and both are enforced.

Notes on the interface

Dialog boxes

The system uses 17 dialog boxes. One shared element serves both patient registration and patient editing, which is why the “New patient” and “Register patient” actions open the same form. The remaining sixteen are specific to a single feature: appointment detail, appointment form, consultation, docket detail, docket POS QR, docket form, inventory history, stock movement, patient profile, patient clinical history, product, service, supplier, therapist, user, archived products, and confirm.

Unused workspace sections

The markup defines two workspace sections that no role can reach. They have no sidebar entry and no entry in the role configuration. They are unused scaffolding from an earlier layout: the Security content was folded into the login screen, and the Validation content into the Audit trail workspace. They render nothing and affect no behaviour.

Authentication and authorization

Authorization is enforced twice, independently. The interface hides actions a role may not perform, so the user is never offered a button that will fail. The application server separately rejects the request at the endpoint with a role check, so the rule holds even if the interface is bypassed.
